Researcher guide

Every report is replayed against the target. Prose is never accepted as proof.

The rule

Don't tell us it's a bug — show us. Your report is replayed verbatim, so write steps and requests we can execute exactly as given.

What we verify

Bug classProof required
idorTwo accounts. Show the victim's object fetched with the attacker's credentials — both raw requests and responses.
xss_reflected
xss_stored		Exact payload with a unique marker, plus proof it executed: screenshot, console output, or document.domain. For stored XSS, include where it renders.

A good report

Steps — numbered, concrete, no filler:

1. Log in as the attacker account (session cookie below)
2. GET the victim's object: /api/profile/alice
3. Response contains Alice's private fields, not Bob's

Raw request — the exact bytes:

GET /api/profile/alice HTTP/1.1
Host: api.example.com
Cookie: session=attacker-session-here

After you submit

You get a private tracking link — keep it. It shows your report's status: received → under review → a decision, plus any questions we send you. If we ask for information, reply on that page; unanswered requests stall the report.

Rules

  • Stay in scope. Out-of-scope tests are rejected.
  • Only test with accounts you created. No access to real user data.
  • No destructive testing: no data modification, DoS, or pivoting.
  • You attest that you reproduced it yourself. False claims lead to a ban.
